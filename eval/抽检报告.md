# AI Trending Radar 介绍质量抽检（2026-10-01）

## 方法

- **样本**：`data/intros/` 缓存中共 28 条介绍，用固定种子 `20261001` 随机抽 20 条（`eval/prepare.py`，可复现）。
  - 评测时的 v2 原文已固定存到 `eval/v2/`（从提交 16cf76d 取回）。线上的 `data/intros/` 在 09-30 上线 v3 时被全部重新生成，复现评测时不要用它。
- **对照材料**：按每条介绍记录的 `readme_sha` 从 GitHub 取回**生成时的那一版 README**，用 `fetch.py` 的同一套规则清洗并截断到 12,000 字符。模型当时看到什么，对照的就是什么。另附仓库元数据。
- **生成模型**：claude-sonnet-5，提示词 v2。
- **评判**：
  - 字数和命令两项由脚本判定（`eval/mechanical.py`）；
  - 其余逐条人工对照 README 判定（由 Claude Opus 5.5 执行，**待本人复核**）。明细见 `eval/findings.json`。

### 评分标准

| 维度 | 判定为问题的条件 | 判定方式 |
|---|---|---|
| 事实偏差 | 与 README 不符，或同一条介绍前后矛盾 | 人工 |
| 夸大 | 超出材料的褒义判断，或选择性呈现不利结果 | 人工 |
| 未标注项目方数据 | 自报的性能数字没标“项目方数据” | 人工 |
| 漏报风险 | README 有明确依据、属于提示词所列风险类型，却没标 | 人工 |
| 风险无依据 | 标出的“风险”只是使用限制、常规流程或设计取舍 | 人工 |
| 格式 | 违反提示词对字段的要求（字数、条数、空值规则） | 脚本 + 人工 |
| 命令可追溯 | quickstart_cmd 能否在 README 中找到 | 脚本 + 人工 |

问题分两级。**重要**：读者会因此得出错误结论。**轻**：不影响对项目的基本判断。

## 重要 bad case（复核前 3 个，复核后 2 个）

1. **gpt-instruct：选择性呈现（夸大）**
   - 介绍把“全量 B 测试 52/66”写成亮点。
   - README 写明 B 层的通过门槛是 66/66，这一版没达标，C 层也因此没跑。
   - 读者会以为这是个好成绩。
2. **codex-with-chatgpt：漏报封号风险**
   - 这个项目的核心就是让 Codex 自动操作付费 ChatGPT 网页版，用订阅额度顶替 API，但 risks 是空的。
   - 同一期里做法几乎相同的 codex-chatgpt-web 标了 3 条风险。**同类项目的判断不一致**，说明风险规则靠模型自由发挥，不稳定。
3. **watermarks-remover：功能描述错误**（本人复核后降为轻微，见文末“本人复核”）
   - 介绍写“保证 Agent 写文件时的清理可靠执行”。
   - 实际上钩子默认是 check 模式，只报告不清理。

## 发现

1. **幻觉比预期少，主要问题在“判断”上。**
   - 20 条里没有凭空编造功能或数字的情况，自报的性能数字基本都标注了。
   - 问题集中在两处：一是亮点怎么挑（选择性呈现、无依据的“迅速走红”）；二是风险标注的松紧（该标的漏了，不该标的标了）。
2. **风险规则同时偏松和偏严。**
   - 漏报的都是“项目本身就在自动化别人的服务”。
   - 误报的都是“使用限制或常规流程”，比如需要联网、需要登录、不接受贡献。
   - 提示词只列了该标什么，没说什么不算风险。
3. **字数“超限”其实是需求没定义清楚。**
   - 提示词写“不超过 40 字”，没说中英混排怎么算，代码里也没有校验。
   - 按字符算，20 条全部超限；按单词算，一条都没超。这不是模型不听话，是规格写得有歧义。
4. **来源冲突没有处理规则。**
   - open-connector 的仓库简介写 1500+，README 写 1,000+。模型两个都用了，同一条介绍前后矛盾。

## 改进建议（提示词 v3）

| 问题 | 改法 |
|---|---|
| 风险漏报 | 明确写：“项目的核心功能是自动操作第三方网页账号（包括 ChatGPT 等 AI 服务的网页版）时，必须标注” |
| 风险误报 | 加反例：“需要联网、需要登录、不接受外部贡献、效果有随机性，都不算风险” |
| 选择性呈现 | “项目方的测试结果如果没达到它自己设定的门槛，要一并说明”；禁止“迅速走红”“增长迅速”这类没有数据支撑的说法；速度、延迟也按项目方数据标注 |
| 字数口径 | 写明“中文字符和英文单词各算 1 字”，代码里加长度校验，超限就重试一次 |
| 上手命令 | README 没有安装命令时返回空；quickstart_note 必须和命令属于同一条路径 |
| 来源冲突 | 元数据和 README 的数字冲突时以 README 为准 |

改完后提示词版本号升到 3，同样的 20 条重跑一遍，再用同一套标准复测，就能得到改进前后的对比。

## 局限

- 样本只有 20 条，来自 28 条的缓存池，不能代表所有类型的仓库。
- 人工判定由 Claude 完成，被评的介绍也是 Claude 写的，可能有同源偏差。2026-10-04 本人已复核全部重要问题和随机 4 条，见文末“本人复核”。
- 只核对了模型看到的 README 摘录，没有验证 README 本身说的是否属实。

## 结论

| 范围 | 结果 |
|---|---|
| 4 个重要问题 | 同意 3 个（gpt-instruct、codex-with-chatgpt、crm）；**watermarks-remover 降为轻微** |
| 随机 4 条（OpenBot、genoffice、artemis、Graft，固定种子 20261004 抽取） | 没有发现判漏、判错 |

**watermarks-remover 为什么降级**：介绍写“保证清理可靠执行”确实与默认行为（只检测、不清理）不符，但用户装上后会马上看到“只报告不清理”的提示，误解很快会被纠正，不会让读者对项目性质得出错误结论，所以按“重要”的定义只算轻微。

**降级后的数字**：v2 重要问题 3 → 2，问题总数不变（16）。v2 → v3：问题 16 → 8，重要问题 **2 → 1**。

## 复核中发现的、评测标准没覆盖的问题：分类会误导项目性质

原分类“安全相关”同时装下了越狱提示词（gpt-instruct）和攻击性红队工具（T3MP3ST），读者容易以为是防护类产品。7 类评测标准里没有“分类是否误导”这一项。

处理方式：
- **不回溯改分数**：评测标准在看结果前就定了，事后加标准再重算会让数字失去可比性，所以 16 → 8 的口径不变。
- **作为产品改动直接修复**（提示词 v4）：
  - “安全相关”拆成“安全防护与合规”“攻击性安全（仅限授权测试）”“越狱与绕过模型限制”；
  - 后两类在页面上用警示样式，标题下附性质说明（`config.yml` 的 `warn_categories`）；
  - 提示词要求按核心功能归类，越狱、攻击类必须进对应分类，不能放进中性分类。
- **验证**：用 v4 提示词重新生成 gpt-instruct 和 T3MP3ST，分别归入“越狱与绕过模型限制”和“攻击性安全（仅限授权测试）”。
- **下一轮评测**：把“分类是否误导项目性质”加为第 8 类标准。
